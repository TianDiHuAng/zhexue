实现说明

这一页写给要改这个库的人：架构、数据长什么样、规则怎么守、坏了怎么修。仓库里的 HANDBOOK.md 是同一份说明的完整版（含字段字典与逐条 SOP），本页是站点版摘要。

一、四层架构

四层单向依赖：内容只写在 data/ 与 sources.json；tools/ 负责校验与渲染；site/ 是产物（也提交进仓库，那只是为了能离线双击打开，CI 每次会用数据重新生成一遍）。改内容永远只改 data，不改 site。

二、生产流水线

顺序固定（D53）：写数据 → 校验 → 生成状态 → 生成站点 → 链检查 → 提交。改完数据跳过 check.py 直接生成，是这份工程最常见的错误来源。

四、校验规则 R1—R23

tools/check.py 的 23 条规则，每条报错都带规则号。最常踩的八条：

规则内容最容易怎么踩
R10needs_verification 与 pending_notes 联动写了「待核」却把标记留成 false
R11内部引用目标必须存在（概念 related 须同单元）引用了别单元的概念 id
R12双源 ≥2；不足须同时标待核并写明待核内容单源条目直接提交
R14概念用法 ≥2 位且说法不同两个人写成同一句话
R19doctrine 四字段／works_detail 三个必填只写书名与备注

六、加一条内容的顺序

  1. 先查重：新建实体前断言 id 与标题全库不存在（D60／D61）——跨区域撞名是最高频返工。
  2. 写数据：在对应单元 JSON 里加对象，字段按上表补齐。
  3. 补来源：须实开核验后才置 verified: true；抓不到就不登记，并把实测结果写进仓库的 BACKLOG_SOURCES.md。
  4. 跑校验：check.py 逐条清零（警告不必清零，但别为清零而注水）。
  5. 重生成：gen_state.py → gen_site.py → check_links.py。
  6. 更新派生清单：relcheck／authcheck／gapscan／thincheck／debtcheck。

七、数字口径

一切统计以 coverage.json（gen_state.py 生成）与各工具输出为准，不抄记忆。特别提醒：「待核实用量」有两个口径 —— DEBT.md（人物／著作／比较）与 DEBT_CLASSES.md（另含概念与争论），两者不可相减。

九、接手第一天做什么

  1. 读仓库的 README.md（是什么）→ DELIVERY.md（到哪了）→ HANDBOOK.md（怎么动）→ DECISIONS.md（为什么这样定规矩）。
  2. 本地跑通六条命令：check／gen_state／gen_site／check_links／dupcheck／refcheck，确认全绿。
  3. 看一次 来源列表 的核验状态，以及 误读索引 的写法。
  4. 动手前记住三句：宁可少一页，不破一条规矩；空着比填错好；宁可不挂，不乱挂。
